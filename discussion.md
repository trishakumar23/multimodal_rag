1. Chunk size
    The current implementation uses a token budget to control the size of textual chunks. However, in a multimodal setting, text token count alone is not sufficient to determine whether a chunk is too large, because it does not account for the visual content associated with that chunk.
    I observed this directly while testing the pipeline on a visually dense page from the 2022 report. The extracted text fit within the configured token budget and therefore resulted in a single chunk, but eight useful images were associated with that same chunk. While the chunk is valid from a text perspective, it contains a large amount of visual information, which could reduce retrieval precision and unnecessarily increase the amount of context passed to a downstream vision-language model.
    I would therefore use two complementary constraints when constructing multimodal chunks: a maximum number of text tokens and a maximum amount of visual content, initially represented by a simple MAX_IMAGES_PER_CHUNK threshold. 
    However, when the visual limit is exceeded, I would not simply split after every N images. Since the pipeline already uses Docling, I would take advantage of the document structure and provenance it extracts to decide where to split. In particular, Docling gives us information such as headings, captions, page provenance and bounding boxes for document elements. The bounding boxes are especially useful because they allow us to reason about the spatial relationship between a figure and nearby text. For example, an image, its caption and the text immediately surrounding it can be treated as a single multimodal semantic unit rather than being separated only because an image-count threshold was reached.

    Conceptually, the strategy would be:
    Text token budget + Visual budget
              ↓
       Is the chunk too large?
              ↓
             Yes
              ↓
````Use semantic/layout boundaries to split
              ↓
````Keep related text + images together````

This would produce smaller and more coherent multimodal retrieval units while avoiding the loss of relationships between figures and their surrounding text. As a further optimization at retrieval time, if a retrieved chunk still contains several images, the images could be ranked against the user's query so that only the most relevant ones are passed to the downstream multimodal model.



2. Image storage
    Since the original PDFs are guaranteed to remain accessible, I would avoid treating extracted image files as the primary source of truth. Instead, I would store a reference to each visual element in the relational database: the source document identifier, page number, bounding box, caption when available, and its association with the corresponding chunk.
    This fits naturally with the current Docling-based pipeline, since Docling already provides page provenance and bounding boxes for detected pictures. Given the original PDF, the page number and bounding box allow us to locate the visual element and recreate its crop when it is actually needed. Keeping this information also provides useful provenance: an image associated with a retrieved chunk can always be traced back to its exact location in the source document.
    I would therefore not store the image binaries directly in the relational database. Permanently extracting and storing every image would duplicate information that is already available in the original PDFs, which becomes increasingly inefficient as the document collection grows.
    There is, however, a trade-off between storage and computation. Recreating an image from its PDF every time it is needed requires rendering the relevant page and cropping the corresponding bounding box, which introduces additional latency. For a production system, I would therefore consider lazy extraction with caching: generate the crop when it is first needed and optionally cache it in object storage for subsequent use. The original PDF reference, page number and bounding box would remain the canonical representation, while the cached image would simply be an optimization and could be regenerated at any time.
    For this take-home implementation, I chose to persist the extracted PNG crops locally and store their paths and metadata in SQLite. This makes the ingestion results deterministic and, importantly for this assessment, makes the multimodal chunks easy to inspect through the HTML debugging interface. At a larger scale, I would favor the PDF-reference approach with optional cached crops rather than permanently duplicating all extracted images.

3. ColPali-like models
    I think a ColPali-like approach is particularly interesting for this dataset because the annual reports contain visually rich pages where information is conveyed not only through text, but also through tables, figures, layout and the spatial relationships between these elements.
    In the current pipeline, Docling first decomposes the document into structured elements and I then reconstruct some of the relationships between them when creating multimodal chunks. For example, the image-association strategy uses caption references and bounding-box proximity to determine which textual chunk an image belongs to. This works well in the pages I inspected, but it also introduces heuristics and potential failure points. A page-level visual retrieval approach preserves the original document representation and therefore avoids having to reconstruct many of these relationships after parsing.
    ColPali-like models are also attractive because their late-interaction, multi-vector representation does not compress an entire page into a single embedding. Different parts of the page can contribute independently to its relevance to a query, which is well suited to pages containing several textual and visual elements.
    However, I would not automatically replace the structured ingestion pipeline. Page-level retrieval has a coarser retrieval granularity than semantic chunk retrieval, which may matter for these reports because a single page can contain several independent topics. The current Docling representation also provides explicit text, tables, headings, captions, bounding boxes and provenance that can be useful for filtering, precise source attribution, debugging and other downstream processing. Multi-vector retrieval can additionally require more storage and retrieval computation than a conventional single-vector dense index.
    For this use case, I would therefore treat a ColPali-like architecture as an alternative retrieval strategy to evaluate empirically rather than assuming it is inherently better. I would build a representative evaluation set containing textual, tabular, visual and layout-dependent questions and compare retrieval quality, latency and index/storage requirements against the current structured chunking approach.
    A further experiment I would consider is hybrid retrieval, combining fine-grained structured chunks with page-level visual retrieval. The structured pipeline could provide precise textual and metadata-aware retrieval, while the visual retriever could recover pages where layout or graphical information is important. Whether the additional complexity is justified should ultimately be determined by retrieval performance on the target query distribution.
